**Повод:** 2026-10-11 smtp.yandex.ru (<IP>) не отвечал на любых портах с прода И локально (ya.ru/imap/чужие SMTP ок) — внешний сбой Яндекса; письма менеджеров молча оставались черновиками (37 «SMTP send failed: Connection timed out»). У Яндекс 360 НЕТ API отправки из ящика — SMTP единственный путь; Postbox (Yandex Cloud) — только как резерв, не делали.

**Что сделано (commit 8bf902c):** `OutgoingMailSender::sendDraft($id, queueOnTransientFailure)` — флаг включён ТОЛЬКО у Mail\Composer и Requests\Mail\ComposeForm (письма людей); авто-рассылки (SupplierReminder, ClientNotification, SendClientDocumentDialog и т.д.) — без флага, старое поведение. Транзиент = «Connection could not be established» / STARTTLS / SMTP 421,450,451,452,454. Обрыв/таймаут ПОСРЕДИ сессии НЕ повторяем (сервер мог принять → дубль клиенту). Поля на черновике `email_messages.send_status(queued|failed)/send_attempts/send_next_attempt_at/send_last_error`; enum DraftSendStatus; OutgoingSendRetryService; крон `mail:send-queued` (каждую мин) → SendQueuedDraftJob (post-send хуки как у композеров, актор=автор). Бэкофф 1,5,15,30,60… всего 12 попыток (`services.mail_outbound.retry_*`), потом failed + колокольчик `outgoing_send_failed`. Cache-lock `outgoing-draft-send:{id}` против двойной отправки. Правка черновика (EmailDraftService::update) снимает с очереди.

**Резервный канал (commits 8873759, f89a0ca):** после `after_attempts` (3) неудач Яндекса попытка идёт через SMTP-сервис доставки, дальше каналы ЧЕРЕДУЮТСЯ (резерв/ящик/…), ошибка самого резерва не хоронит письмо. Настройка — «Настройки» → блок «Резервный канал отправки» (Livewire Admin\Settings\MailFallback; РОП/директор/админ): app_settings `mail.fallback.*`, ключ API зашифрован Crypt (смена APP_KEY → ввести заново); источник правды MailFallbackSettings (пока блок не сохраняли — .env MAIL_OUTBOUND_FALLBACK_*). Провайдер: у компании ТОЛЬКО классический Unisender (маркетинг, unisender.com; SPF include/DKIM `us` — его), Unisender Go НЕТ → SMTP Unisender даёт 535 Bad credentials, классика не годится (нет SMTP, sendEmail = список контактов + отписка). Postbox заведён 2026-10-11 (облако cloud-markyellow/каталог default, SA postbox-user с ролью postbox.sender, API-ключ id aje31ove2lgs5v1f35ko scope yc.postbox.send; SMTP postbox.cloud.yandex.net:587 STARTTLS, логин=ID ключа, пароль=секрет — сверено с докой); адрес myzip.ru+DKIM (2 CNAME в RU-CENTER nic.ru) — на момент записи не создан. ГЛАВНЫЙ ВЫВОД: в сбой 2026-10-11 лёг ВЕСЬ Yandex Cloud (баннер «Недоступность зон») — smtp.yandex.ru И Postbox недоступны и с прода, и локально, даже :443 → Postbox НЕ независимый резерв. Независимый: smtp.bz — ВКЛЮЧЁН 2026-10-11 как резервный канал (аккаунт компании есть, тариф «Лаборатория FREE» — проверить лимиты; домен myzip.ru подтверждён DKIM/SPF/CNAME; трекинг ВЫКЛ, транзакции ВКЛ; connect.smtp.bz:587 STARTTLS; проверка подключения и тестовое письмо прошли). Postbox — запасной, адрес+DKIM не доделаны, баланс YC был −35₽. Таймаут резервного SMTP 20с (MailFallbackSettings::TIMEOUT_SECONDS). `email_messages.sent_via` = имя канала, в треде «↪ Отправлено через …». Ключ API пользователь вводит САМ в форме (мне вводить ключи нельзя).

**Монитор SMTP (commit 5893e67):** `mail:smtp-health` каждую минуту — TCP-проба SMTP активных ящиков (8с), состояние в Cache `smtp-health:host:port` (TTL 180с), смены в лог «SMTP health: down/back up». Письмо человека при known-down Яндексе СРАЗУ уходит резервом (без 20 мин очереди); резерв отказал → очередь. С commit 9a64f7c резерв используют И авто-письма: sendDraft без флага очереди тоже переключается (known-down / не соединился / OAuth не обновился → сразу резерв), sendAdHoc тоже; SystemNotificationMailer, SupplierCcInboxService, недельный отчёт, MailForwarder переведены на sendAdHoc (раньше строили SMTP Яндекса напрямую; дубль транспорта в MailForwarder удалён). Любая новая отправка — ТОЛЬКО через OutgoingMailSender (sendDraft/sendAdHoc), не buildSmtpTransport напрямую. AppendToSentFolderJob: 8 попыток ≈5ч (хранилище Яндекса в сбой отвечает «NO [UNAVAILABLE] APPEND»).

**Разбор 2026-10-11:** 7 застрявших писем Головнева отправлены через smtp.bz (requeueNow+SendQueuedDraftJob), ответ поставщику #2588663 вручную привязан к inquiry 7022; 23 мусорных черновика авто-напоминаний удалены, SupplierReminderService теперь удаляет черновик при сбое (commit 7584472).

**Диагностика «письмо не ушло»:** `select id,send_status,send_attempts,send_next_attempt_at,send_last_error from email_messages where is_draft and send_status is not null`; лог `OutgoingSendRetry: queued|gave up`; проверка SMTP с прода `timeout 8 bash -c "</dev/tcp/<IP>/465"`.
