**Супплаерные письма не должны быть reply-якорем клиентского треда (fix 2026-08-24, M-2026-11814):** «Ответить» из заявки слал КП ПОСТАВЩИКУ. Причина: письма rfq@mzcorp.ru (mailbox#17 shared, SupplierCcInboxService — CC внешней переписки с поставщиками) и супплаер-реплаи с разорванным тредом линковались к related_request_id клиентской заявки, но НЕ к инквайри (supplier_inquiry_id=NULL) → проскакивали в клиентский тред (фильтр был только `whereNull(supplier_inquiry_id)`) и, как последнее внешнее inbound, становились reply-якорем. **ВАЖНО (design): rfq@ CC письма ПО ДИЗАЙНУ видны во вкладке «Переписка»** (SupplierCcInboxService docblock: «category=supplier_reply → видно во вкладке Переписка» + уведомление менеджеру с rfq@; клиентскую заявку НЕ создаёт). Прятать их НЕЛЬЗЯ — первый заход я ошибочно исключил `category=supplier_reply` из тред-запроса Detail → письма rfq@ без инквайри исчезли отовсюду (регресс M-2026-12942, где инквайри нет вообще), ОТКАЧЕНО. Финальное поведение (по требованию заказчика «всё как раньше, только отвечать клиентам, а не таким отправителям»): супплаер-письма ВИДНЫ в треде, inline reply-кнопки на ВСЕХ письмах (как раньше), но ОТВЕТ всегда КЛИЕНТУ. Механизм: (1) blade `$lastInbound` (якорь шапки «✉ Ответить») пропускает супплаерные (`$isSupplierMsg` = category supplier_reply OR supplier_inquiry_id!=null) → шапка отвечает последнему письму КЛИЕНТА с цитатой; (2) `ComposeForm::openFromMessage` — если целевое письмо супплаерное, вместо reply поставщику открывает `createCompose` (ответ КЛИЕНТУ заявки) + тост. Т.е. reply на письмо поставщика из клиентского треда МОЛЧА перенаправляется на клиента (не глушится). Отвечать поставщику — из раздела «Поставщики». Тред-запрос Detail — только `whereNull(supplier_inquiry_id)` (rfq@ CC без инквайри ВИДНЫ по дизайну). 6 орфанов M-2026-11814 привязаны к inquiry 3316 → в карточку поставщика.

**Линковка ответа поставщика: пара отправитель+M-код, домен-fallback (fix 2026-08-24):** ответ поставщика не привязывался к инквайри (уходил в irrelevant/фантом) по ДВУМ причинам. (1) `matchInboundBySubject` был загорожен `looksLikeRfqReply`, требующим фразу «запрос расценки»/«price request» — а тема запроса бывает ПРОИЗВОЛЬНОЙ: часть менеджеров (напр. Курзаев, ящик 7) шлёт запрос поставщику со СВОЕЙ почты со своей темой «Запрос M-YYYY-NNNN» (не наш авто-формат SupplierDispatchService «Запрос расценки — [код]»; 45 таких инквайри, rfq_token NULL, регистрируются через createFromOutbound по IMAP Sent). Снят фразовый гард — дискриминатор = пара `supplier_email + M-код в теме инквайри` (клиент не значится supplier_email инквайри своей заявки). MailRouter пробует позитивный матч безусловно (до фразового fallback). (2) Поставщик отвечает с ДРУГОГО адреса того же домена (слали на <адрес>, ответ с <адрес>) → точное совпадение почты не срабатывало. Добавлен fallback по домену (`split_part(supplier_email,'@',2)` + M-код), ТОЛЬКО для корпоративных (const FREE_MAIL_DOMAINS: mail.ru/gmail/яндекс/… исключены — общий домен). Кейс M-2026-12940/inq3721. Ручная привязка: `app(SupplierInquiryService)->matchInboundBySubject($msg)` → `attachMessage` → `SupplierOfferParser::parse`.

**Парсинг офферов — доставка/итог НЕ в цену позиции (fix 2026-08-24):** `ParseSupplierReplyPrompt` не запрещал включать доставку/упаковку и брать документный ИТОГ как цену позиции. ## Тред-центричный матчинг (ответы) — КОНСЕРВАТИВНО
Подавление ответов **только по цепочке треда** зарегистрированного запроса (явно помеченного ИЛИ созданного send-time). Без авто-подавления «любой ответ от контакта-поставщика». Ручная кнопка-fallback (ниже) **закрывает** заявку.

## Данные
- `supplier_inquiries` (App\Models\SupplierInquiry): supplier_email/name, subject, `thread_root_id` (корень цепочки треда — Message-ID нашего исходящего запроса из In-Reply-To/References пойманного ответа), `related_request_id` (опц., чаще null), status (open/closed), created_by_user_id, notes.
- `email_messages.supplier_inquiry_id` (nullable FK nullOnDelete) — письмо = переписка с поставщиком.
- `EmailCategory::SupplierReply` ('supplier_reply', label «Переписка с поставщиком») + `ClosedLostReason::SupplierReply` («Не заявка — переписка с поставщиком»).

## Логика — App\Services\Supplier\SupplierInquiryService
- `matchInbound(msg)` — СТРОГО по цепочке треда: refs=(in_reply_to + references_header) ∩ ({inquiry.thread_root_id} ∪ {message_id уже прикреплённых писем}). Никаких subject/email-эвристик (чтобы «только помеченные треды»). Только inbound.
- `markFromRequest(request, by)` — создаёт/находит inquiry по корню треда, прицепляет ВСЕ письма заявки (where related_request_id=req.id) + originating.
- `attachMessage(inquiry, msg)` — supplier_inquiry_id + для inbound category=supplier_reply + categorized_at=now() (чтобы не утекло в /mail-review [фильтр category=irrelevant+categorized_at] и крон mail:categorize не трогал).
- `isKnownSupplier(email)` — есть ли хоть один inquiry (для UI, НЕ для подавления).

## Пайплайн (гард + defense-in-depth)
- `MailRouter::route` inbound: ПОСЛЕ cross-mailbox dedup, ДО categorize и ДО replyLinker — `matchInbound` → совпало → attachMessage + `return` (заявка не создаётся, LLM не зовём).
- `IncomingMailProcessor::processIfRequest`: defense-in-depth после related_request_id-гарда (cron mail:create-requests/categorize минуют router) — тот же matchInbound → attach + return null.
- **Первый ответ в НЕпомеченном треде всё ещё создаёт фантом** (until marked) — это и есть «только помеченные треды».

## Ложный «отказ» в ответах поставщика — ТРИ независимых корня (2026-07-15)
Симптом: `SupplierOfferParser` помечает ответ с ЦЕНОЙ как refused/skipped (карточка /dashboard/suppliers/{id} показывает «отказ» вместо цены). Три разные причины — все три пофикшены и задеплоены (commits d7cf310, 4bed160, 5c6d3a1):

Foxmail «发件人：» и «From:Name» без пробела, длинные линии-разделители, «… wrote:/пишет:», >-цитаты) с гардом против bottom-posting (<30 симв нового текста сверху → не режем). Разбираем только НОВЫЙ текст ответа.
3. **Имя позиции на инквайри ≠ отправленному в письме** (кейс inquiry 1095: письмо «Трансформатор … Kone KM89794G02», а `supplier_inquiry_items.item_name` хранил сырое «Катушка питания платы» = ri#16093.parsed_name). Так перепарсены 1231/1143/1095 → показывают цены. Аудит промахов: `SupplierOffer` where outcome=refused + raw_quote с ценовым сигналом (регексп на digits/USD/долл/руб) — на 2026-07-15 из 6 refused лишь 1 был ложным (offer#52/1095, оказался корнем №3), остальные — настоящие отказы.

Наши исходящие реплики торга офферами не становятся (парсим только inbound).

## Уникальный RFQ-токен в теме → детерминированный матч ответа (2026-08-11)
Снабжение шлёт RFQ поставщикам НАПРЯМУЮ (позиция-центрично, SupplierProcurementDispatchService, related_request_id=null) + ведёт активную НЕ-RFQ переписку (закупки/отгрузки/рекламации). Оба диспетчера: SupplierProcurementDispatchService ставит токен напрямую при create; SupplierDispatchService (request-центричный) добавляет маркер в тему через `app(SupplierInquiryService)->rfqMarker(generateRfqToken())`, а `createFromOutbound` извлекает токен из темы (`extractRfqToken`) и сохраняет. Матч ответа: `SupplierInquiryService::matchInboundByRfqToken` (regex `/\[RFQ-([A-Z0-9]{4,12})\]/i` → inquiry по rfq_token) — ПРИОРИТЕТНО над matchInbound/matchInboundByAnyCode, и в MailRouter inbound, и в ingestSupplierMessage. Токен уникален на инквайри = (заявка/пул × поставщик) → точно знаем кто/по чему ответил; переписка без токена не липнет к RFQ. Хелперы: generateRfqToken (Str::random(7) upper, unique-retry), rfqMarker, extractRfqToken. Работает для НОВЫХ рассылок (старые инквайри без токена — тред/код-матч). Шаблон RFQ просит «сохранять тему переписки».
