Кейс M-2026-5303 → M-2026-6764: клиент ответил в закрытый тред (та же кнопка M06219, 5303 закрыта «нет ответа» за 3 дня до), а система создала НОВУЮ 6764 вместо оживления 5303. Пользователь ждал реанимации.

**Штатный поток (наследование, Phase 2.1):** `InboundReplyLinker` при матче ответа по In-Reply-To/References на ТЕРМИНАЛЬНУЮ (closed_*) заявку НЕ привязывает к ней и НЕ падает в fallback «открытые заявки клиента» (чтобы не прицепить к чужой открытой — кейс M-2026-1558); пишет `inheritance_candidate_id` в `email_messages.detected_artifacts`, возвращает null → создаётся НОВАЯ заявка. После парсинга позиций `RequestItemPersister` диспатчит `CheckInheritanceJob(new)`. Тот через LLM `InheritanceCandidateChecker` (is_continuation, conf; порог services.inheritance.confidence_threshold=0.7) при подтверждении → `RequestInheritanceService::linkChild` (новая = child закрытой, общий inheritance_group_id, item-маппинги; НЕ реанимация). Поля: requests.inheritance_group_id/inheritance_role(parent|child)/inheritance_parent_id. reanimate() существовал, но линкер его НЕ звал.

**Реанимация ловит и совпадение по catalog_item (fix 9386011, кейс M-2026-8786→10286):** `shouldReanimateInPlace` раньше считал «те же позиции» ТОЛЬКО по совпадению артикула (itemMappings source=auto_article). Клиент форварднул НАШЕ ЖЕ КП на закрытую-по-тишине 8786; позиция «Устройство привода дверей» из КП PDF без чистого артикула, но с тем же catalog_item 19223, что у родителя → артикульный матч 0/1 → создался child 10286 вместо реанимации. Ключевой вопрос заказчика: реанимировало бы с ТОЙ ЖЕ почты? НЕТ — почта отправителя в развилке НЕ участвует (в inheritance ни одного client_email/from_email); решает 0-vs-N позиций + item-match. Фикс: полным совпадением позиции считаем И совпадение `catalog_item_id` (не только auto_article) — `$new` items с catalog_item_id ∈ parent catalog_ids. Downstream-гард (нет quotations/invoices/outbound_quotes у новой) + LLM is_continuation остаются. 10286 не откатывали (уже invoiced).

**Гибрид (заказчик выбрал; commit 44ad7e7, на проде):** в `CheckInheritanceJob` после подтверждения продолжения — развилка:
- **Реанимировать СТАРУЮ in-place** (переоткрыть под тем же номером, свернуть свежую новую) ЕСЛИ: candidate именно `closed_lost` + причина `no_client_response_to_quote|no_client_response_to_clarification` + closed_at в окне `services.inheritance.reanimate_max_days`(=45) + ВСЕ активные позиции новой совпали по АРТИКУЛУ (suggestLinks source=`auto_article`, не similarity) + у новой нет КП/счёта (quotations/invoices/outbound_quotes). Действие (`reanimateInPlace`, одна транзакция): письма новой → related_request_id старой; удалить client_notifications_sent новой (без FK); `RequestStateService::reanimate(candidate, source=inbound, reassessAssignee:true, event=reanimate_from_reply)`; `$newRequest->delete()` (каскад чистит items/state/assign/views/ai_decisions; письма уже перевешены). При любой ошибке — откат + fallback в linkChild (данные целы).
- **Иначе → наследование** (linkChild, как раньше): другие/новые позиции, similarity-матч без артикула, closed_won, старше окна, есть downstream.

**Реанимация возвращает на PEAK-веху (commit 321463b):** `RequestStateService::reanimate()` раньше всегда ставил `in_progress`, даже если КП/счёт уже выдавался до закрытия → выглядело как новая первичная проработка. Теперь возвращает на `peak_status` (Quoted/UnderReview/AwaitingInvoice/Invoiced), кроме Paid/terminal; если вехи не было — in_progress. Влияет на ВСЕ пути реанимации (гибрид, ручная кнопка «Реанимировать», revival-ответы). Пример: 5303 peak=quoted → реанимация в `quoted` («КП отправлено»). NB: путь НАСЛЕДОВАНИЯ (linkChild, другие/добавленные позиции) оставляет child в in_progress — у него свой КП ещё не выдан.

Строгие гарды делают деструктивную ветку (удаление свежей заявки) безопасной; худший случай — дубль слит в переоткрытый оригинал (данные на оригинале). Проверено dry-run на 5303/6765: совпадение по M06219 → REANIMATE. FK: у requests каскадят request_items/state_changes/assignments/user_views/quotations/invoices/ai_decisions/outbound_quotes/delegations; email_messages.related_request_id и client_notifications_sent.request_id — БЕЗ FK (обрабатываем вручную). Кейс 5303/6765 НЕ бэкфилен (уже связан как child). Связано: [[possible-new-request]], [[revival-offer]], [[request-access-delegation]].

## Ответ-ТЕКСТ без номенклатуры → тоже реанимация (commit ec9c158, 2026-07-20)
Дыра в `shouldReanimateInPlace`: гард «все позиции новой совпали по артикулу» начинался с `if ($newActive === 0) return false;` — то есть ответ БЕЗ номенклатуры («когда отгрузите?», «аварийная ситуация, нужно быстрее») никогда не мог реанимировать оригинал и всегда падал в наследование, плодя дубль-наследника с КЛОНИРОВАННЫМИ позициями. Логика вывернута: ноль позиций = клиент ничего нового не заказал = сильнейший сигнал продолжения. **Фикс:** требование совпадения по артикулу применяется ТОЛЬКО когда позиции есть (`if ($newActive > 0) {...}`); ноль позиций реанимацию разрешает. Безопасно, т.к. к этой точке продолжение подтверждено дважды — жёсткий матч `in_reply_to` к терминальной заявке (`matched_by=in_reply_to_terminal_request`) + LLM `is_continuation` ≥ 0.7; постпродажа отсечена раньше в `rerouteAsPostSale()`.
**Канон-кейс M-2026-7976 → M-2026-8874:** 20.07 в 08:00 крон авто-закрытия закрыл заявку (`no_client_response_to_quote`), в 10:50 клиент ответил на НАШЕ же напоминание о КП («аварийная ситуация, ищем поставку побыстрее» — не отказ; интент прочитал как `postponement_request`), в 10:52 создан дубль с `linked_by=system_reminder_fallback`. КП 360908 и № 1С остались на старой, живой диалог уехал на новую. Ремедиация: `reanimate()` старой (вернулась на peak=quoted) → `RequestMergeService::merge` дубля в неё (позиция схлопнулась как дубль). См. [[autoclose-inactive]] (пауза после напоминания — вторая половина того же сбоя), [[request-merge]].
