**HTML-only письма → 0 позиций → вечный pending (fix 43264b2, M-2026-9508):** `parseItemsFromInboundMessage` выбирал тело так: `$rawBody=body_plain`, а html брал только при `bodyPlainLooksBroken(plain)` ИЛИ `htmlHasStructuredTable(html)`. Если письмо HTML-only (нет text/plain части → `body_plain` ПУСТ, не «битый»), а запрос — простой текст в html («Прошу КП: 1. M00613 - 2 шт», не таблица) — обе проверки false → парсил пустоту → 0 позиций → заявка навсегда в `pending` (скрыт из пула) → НЕ назначалась. Так застряли 5 заявок с мая. Фикс: `useHtml` также при `trim(body_plain)===''`. Корень глубже — `MessagePersister` пишет `body_plain=getTextBody()` без html→text fallback; парсер-fallback это закрывает (категоризатор/прочие промпты fallback уже имели). Грабля-2: ре-парс pending-заявки (`just_created=false`) извлекает позиции и ставит assigned_user_id, но статус pending→assigned НЕ переключает — доводить вручную.

**unified вернул 0 → fallback на split (fix f8fd5fb, M-2026-9794):** раньше unified-путь возвращал результат сразу (даже пустой) — fallback на split был ТОЛЬКО при исключении. Кейс: письмо «Защелка аварийного тормоза GO509 P2 шт 5» + фото этой же детали → pipeline пошёл unified (есть фото), но vision вернул 0 несмотря на полный контекст (текст+фото в одном вызове — `extended_body_chars` в логе подтверждает, что текст передавался). Фикс: если `$unifiedItems` пуст — проваливаемся в split-путь (текст+фото парсятся раздельно + дедуп). На кейсе split дал позицию из ОБОИХ источников (`vision_photo` + `email_body`, оба qty=5), дедуп свёл в 1. ОТКРЫТО: почему unified недоизвлекает «одна строка + фото детали» — тюнинг промпта ParseItemsUnifiedPrompt, риск регрессий. Грабля-2: qty у RequestItem — колонка **`parsed_qty`** (НЕ `qty`; `$it->qty` вернёт null — колонки нет); при ре-парсе бывает разброс LLM (10 vs 5).

**Инлайн-фото как фото позиции (fix af077de, M-2026-9365):** `EmailAttachment::scopeBindablePhotos` отсекал ВСЕ `is_inline=true` (диалог «Сменить фото» говорил «нет image-вложений»), но клиенты встраивают реальные фото в тело письма (inline, cid). Теперь отсекаем только мелкие инлайн (< `INLINE_PHOTO_MIN_BYTES`=50КБ — подписи/логотипы), крупные оставляем. Scope используется только для привязки фото (не для парсинга).

**ReplyParseGate игнорировал вложения (fix 9072fec, M-2026-9340):** решал парсить ли reply ТОЛЬКО по тексту (сигналы шт/артикул/прошу в `defaultSignals`), вложения не смотрел. Клиент вторым письмом форварднул наше «Предложение МЗ-355979.pdf» (с КВШ-позицией), текст-cover Fwd без сигналов → skip → позиция из PDF потеряна. Фикс: `hasStructuredDocAttachment` — pdf/xls/xlsx/docx/csv во вложении → shouldParse=true независимо от текста (служебные отсеет relevance-гейт; ФОТО НЕ триггерят — по ним осторожность из-за M-2026-0759). Грабля-2: persister НЕ пишет позиции в терминальную (closed_won/lost) заявку — 9340 была won, дописал вручную RequestItem::create + catalog_item_id по sku.

`RequestItemParsingService::parseItemsFromInboundContent` — разбор позиций входящей заявки. Два пути (лог-маркер `pipeline summary` → `"path"`):

- **unified** — ОДИН Vision-вызов видит subject+тело+ссылки+все фото сразу → одна выдача, дублей фото-vs-текст нет. Включается при: есть фото, ≤8 фото (`MAX_UNIFIED_IMAGES`), **нет тяжёлых номенклатурных вложений** (`$heavyStructured` пуст).
- **split** — vision по фото + text по телу + извлечение из pdf/xls раздельно, потом дедуп. Здесь и рождались дубли: один товар, описанный в фото без атрибута и в тексте с атрибутом, `dedupeWithinList` не склеивал (разные имена, нет артикулов).

**Relevance-гейт вложений (Часть A):** `classifyHeavyAttachmentRelevance` (gpt-4o-mini) на каждый heavy pdf/xls — несёт ли файл товарную номенклатуру. Служебные (реквизиты, счёт на оплату, договор, сертификат) → `is_nomenclature:false` → выбрасываются из `$heavyStructured` и `$structuredAttachments` (лог `dropped non-nomenclature heavy attachments`). Так банковский PDF больше не рубит unified. Fail-soft: ошибка/неуверенность → `true` (не теряем позиции).

**LLM-консолидатор split-пути (Часть B):** `consolidateSplitItems` — если в split позиции из ≥2 разных `__source`, финальную выдачу собирает LLM (`parsing_model`) поверх `dedupeWithinList`: склеивает один товар из разных источников, переносит глобальные атрибуты на весь набор, явно разные товары сохраняет. Fail-soft → `dedupeWithinList`.

**Killswitch'и (config services.openai, дефолт on):** `attachment_relevance_enabled`, `attachment_relevance_model`, `consolidation_enabled`. Промпты: `ClassifyAttachmentRelevancePrompt`, `ConsolidateParsedItemsPrompt`.

**Канонический баг-кейс:** M-2026-4011 — клиент просил 6 кнопок (символы -1/1/3/4 + 2 стрелки, красная подсветка), приложил фото + `реквизиты АЛЬФА-БАНК.pdf`. PDF рубил unified → split → vision-набор без подсветки (6) + text-набор с подсветкой (5) = 11 позиций. Связано с [[duplicate-badge-numeric-token]] (бейдж «возможно дубль» там же мазал на разные кнопки).

Проверка без записи (parser НЕ персистит — persist отдельным шагом в ParseRequestItemsJob): `app(RequestItemParsingService::class)->parseItemsFromInboundMessage($msg)` на проде через tinker.

**Чистый форвард без преамбулы → 0 позиций (fix 2026-08-10, кейс M-2026-11504):** `EmailTextCleanerService::cleanInboundReferenceText` при обнаружении forwarded-блока (extractForwardedContent, маркер «Пересылаемое сообщение»/Forwarded/Перенаправленное) ВСЕГДА отдавал парсеру только преамбулу (`$original`), forward-блок отбрасывал — защита от дублей в ОТВЕТЕ с процитированной нашей КП (кейс #349). Но при ЧИСТОМ форварде (клиент переслал сам запрос, своего текста сверху НЕТ) преамбула пуста → парсер получал пустоту → 0 позиций → заявка висит в pending. Фикс: если `trim(removeSignature(original))` <10 симв → вернуть `removeSignature($forwarded)` (forward-блок = заявка). Кейс: <адрес> шлёт «Fwd: (Без темы)», запрос («Ролик направляющий башмака кабины ELEX 80х30мм 8 шт») в блоке. Перепарс: `requests:reparse-items M-2026-11504 --apply`. Открытый свип: заявки с 0 позиций + чистый форвард (маркер в body_html + пустая преамбула).

**Инлайн-картинки из процитированного КП-треда (fix 67844d8, 2026-08-14, M-2026-12063):** клиент прислал наше же «Предложение МЗ-344330» (наш outbound-КП, OutboundQuote с товаром M33232) со словами «обновите КП». Тело-текст цитаты `EmailTextCleanerService` отсёк корректно, наш КП-**PDF** отсёк `isOwnOutboundDocument`. НО инлайн-картинки письма (5 PNG-спеков Torin Drive, `is_inline=1`, принадлежат процитированному КП-треду) уходили в Vision — отбор картинок фильтровал ТОЛЬКО по mime `image/*`, игнорируя `is_inline`. Vision разобрал их в 2 неверные OEM-позиции (Шкив TS `2022特1559-1`, PM Traction Machine `ER2D-101P7B` Torin Drive) вместо товара M33232 из самого КП → `catalog_item_id=NULL`, нет M-кодов. Фикс в `parseItemsFromInboundContent` (сразу после гейта ownDocs): **если присутствует НАШЕ КП/счёт (`$ownDocs` непуст) → исключаем `is_inline` картинки из `$imageAttachments`** (это картинки цитаты, не новый фото-запрос; наш КП = источник позиций). Не-inline фото остаются. Проверено dry-parse msg 75998: было 2 OEM-позиции → стало 1 «КВШ» из тела, инлайн-спеки отброшены. Принцип заказчика: в цитату лезем когда в своём тексте НЕТ заявки; но если приложено НАШЕ КП — оно источник. Дискриминатор — `isOwnOutboundDocument` по имени файла.

**Part 2 — засев позиций из нашего КП (fix 5695907, 2026-08-14):** когда клиент прислал наше КП обратно, у заявки не остаётся каталожных позиций (КП-PDF и инлайн-спеки в разбор не идут). `App\Services\Request\OwnQuoteRequestItemSeeder::seedForRequest(Request, ?sourceMessageId)`: если у заявки НЕТ активных каталожно-сматченных позиций — берёт матченные строки нашего КП (`outbound_quotation_full`, status matched/parsed, `matched_catalog_item_id` not null, не analog) → создаёт RequestItem с `catalog_item_id`, `data_source='own_quote_seed'`; деактивирует несматченный авто-шум ИЗ письма-источника КП (`source_email_message_id`=sourceMessageId, не manual). Гард «есть сматченная позиция → выходим» защищает нормальные заявки (КП сделан ИЗ них). Идемпотентно. Хуки в ОБА джоба (гонка КП-vs-позиции): `ParseOutboundQuoteJob` (после match/enrich, для OutboundQuotationFull) + `ParseRequestItemsJob` (после persist), оба non-fatal. Аналог существующего `seedRequestItemsFromInvoiceIfEmpty` (но гард «нет СМАТЧЕННЫХ», а не «нет активных»). Проверено на 12063: `request:reparse --reset` (гоняет джоб sync → хук) → неверные OEM-позиции ушли, «КВШ» из тела деактивирована, засеян M33232 из КП; доп-позиция «Тяговые канаты» из reply-письма сохранена (при её парсе заявка уже имела M33232 → гард hasMatched → сидер не тронул). ГРАБЛЯ инструмента: `requests:reparse-items` зовёт parser+persister НАПРЯМУЮ (в обход джоба) → хуки НЕ срабатывают; для триггера хуков нужен `request:reparse` (Bus::dispatchSync ParseRequestItemsJob). ОТКРЫТО: кейс «КП процитировано номером, но НЕ приложено файлом» не ловится (можно расширить на CitedOutboundQuoteRouter).

**Storefront-ссылки mylift.ru/?code=SKU → каталог, не парсим свой сайт (fix 573d7d7, 2026-08-18, M-2026-12580):** клиенты шлют «Можно КП на N шт https://mylift.ru/?code=MXXXXX». Парсер фетчил НАШУ же страницу (`fetchLinkedUrlsForPrompt`→InboundUrlFetcher); при пустом/медленном фетче (кэш заполнялся ПОЗЖЕ парса — 17:59 vs парс 17:28) LLM получал голый код и ВЫДУМЫВАЛ имя. Кейс: code M00152 (=«Контактный мост перемычка Вертолет», OEM Schindler 505404) → галлюцинация «Масленка для башмака кабины Schindler» (это реальное имя соседнего M00153/M00466, дословно есть в чужих заявках — LLM потянулся к типовому каталожному имени). КОД M00152 и каталог-матч (21607) были ВЕРНЫ — кривым осталось только `parsed_name`; отправленный КП №364587 был на правильный товар. Побочка: тексто-sticky роутинг (`AssignmentService::pickStickyByText`, «Sticky 🔤 текст») затем связал заявку с чужой масленко-заявкой ПО этому кривому имени (следствие, не причина). **Фикс:** `RequestItemParsingService::ownStorefrontCatalogBlocks` — regex `mylift.ru|myzip.ru/…?code=(M\d{3,})` в теле → резолв SKU в каталоге → авторитетный блок «Товар из нашего каталога: имя · артикул · бренд · OEM» в linkedUrlsText (независимо от web_fetch.enabled; живой фетч этой же страницы не дублируем — `isOwnStorefrontUrl`). LLM получает точное имя. Точечно 12580 поправлен (parsed_name←catalog). Проверка: `ownStorefrontCatalogBlocks('...code=M00152...')` → «Контактный мост… M00152… SCHINDLER… 505404».

**Позиции из НАШЕГО КП и карточки предприятия (fix 2026-08-11, M-2026-11637):** пост-продажное письмо «пришлите договор» + 2 вложения: наш КП «Предложение МЗ-362628.pdf» (клиент приложил обратно) и «Карточка предприятия АРИТ.docx» (чистые реквизиты). Force-создание («это заявка») → 4 фейковые позиции: часть из нашего КП, часть Vision ВЫДУМАЛ из docx-реквизитов. Два фикса в parseItemsFromInboundContent: (1) `isOwnOutboundDocument($filename)` — отсекаем НАШИ исходящие КП/счета по имени файла (regex «предложение мз-\d{3,}» / «сч[её]т…мз» / «\bмз-\d{5,}»), клиент часто прикладывает наш КП обратно; (2) релевантность-гейт `classifyHeavyAttachmentRelevance` перенесён на ВСЕ структурные (было только heavy pdf/xls) ДО split — docx-карточка предприятия минула гейт и Vision галлюцинировал позиции из реквизитов. Данные: КП-номер 362628 = собственный КП заявки (outbound_quotes.document_number → request_id); КП-позиции просочились в request_items — удалять их из заявки (КП oq цел). Оба fail-soft: при ошибке/неуверенности вложение считается номенклатурным.

**House-brand как бренд позиции — Vision-галлюцинация (fix 39fd520, 2026-08-20, ri#24363 req 11669):** Vision на фото БЕЗ видимого бренда подставлял «Мой ЗиП» (наше же название, из контекста) в parsed_brand. Кейс: фото «Контактный мост ДШ» (чёрный контакт + штангенциркуль, бренда нет) → parsed_brand=«Мой ЗиП»; в теле письма «Мой ЗиП» нет, на детали нет. Массово: 144 активные позиции. Фикс `RequestItemPersister::sanitizeParsedBrand`: обнуляет house-brand'ы (const HOUSE_BRANDS: мойзип/myzip/мойлифт/mylift/ооомойлифт/ооомойзип/mzcorp, норм. lower+без пробелов/точек/дефисов) на create (стр ~181) и в fillBrandIfEmpty (reply/reparse). Бэкфилл: 145 очищено. Наш house-brand НИКОГДА не OEM-бренд клиентской позиции. Каталожные привязки не трогали.

**Длинные ТЗ частями (09.11.2026, ДМА тендер MZ2026-00483, коммиты 4c679024/b2b5b31f/3cf5b2c1):** 190 строк в xlsx + тот же перечень в docx давали 59 позиций — модель обрывает длинный перечень в ОДНОМ вызове (60 из xlsx, 56 из docx), а LLM-консолидатор (`consolidateSplitItems`) так же резал 360 кандидатов до 167, и склейка по артикулу между двумя файлами суммировала qty (1+1). Фикс: `parseFileTextInChunks` — текст файла >30 строк/18k символов частями по 30 со шапкой (7 мин на такое ТЗ; `ParseRequestItemsJob::$timeout=900`, нужен `DB_QUEUE_RETRY_AFTER` > 900 — на проде 1900); `extractFromExcel` склеивает переносы в ячейке (строка = позиция) и читает шире Z; `dropRepeatedDocumentLists` — файл, на ≥60% повторяющий больший, отбрасывается; >40 позиций (`CONSOLIDATION_MAX_ITEMS`) — без LLM-консолидатора; в `dedupeWithinList` строки ОДНОГО источника с общим артикулом, но разными числами в названии не склеиваются (D02 25 А ≠ D02 35 А). Итог: 186 позиций. Тесты `tests/Unit/Services/FileTextChunkingTest.php`.
