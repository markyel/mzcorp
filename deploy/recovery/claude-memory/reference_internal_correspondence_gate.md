Правило (по требованию заказчика): на статус/позиции заявки влияют ТОЛЬКО inbound-письма, где заказчик на одной из сторон (отправитель ИЛИ получатель). Внутренняя переписка сотрудников про заявку — нет.

Кейс **M-2026-6071**: письмо руководителя менеджеру (`<адрес>` → `<адрес>`, обе @myzip.ru; в CC личный `<адрес>` — не заказчик) привязалось к треду и было классифицировано как ответ клиента → `ai_auto_apply` «КП отправлено» → «На согласовании». Заказчик заявки `<адрес>` в письме отсутствовал.

**Гейт** — `InternalSenderDetector::affectsRequestStatus(EmailMessage, ?clientEmail): bool` (commit ea3b769):
- отправитель ВНЕШНИЙ (`detect()===null`) → true (вероятно заказчик/его коллега);
- отправитель НАШ → true только если `clientEmail` явно среди получателей to/cc; иначе false;
- clientEmail пуст → false (не подтвердить заказчика при нашем отправителе).

Грабля первой версии: делал `isInternalOnly` = «все стороны наши» — ломалось на внешнем CC (личный yandex/gmail коллеги делал письмо «не-internal»). Правильный критерий — «заказчик на стороне», а не «все внутренние».

**Точки применения (единый источник — метод детектора):**
- `InboundIntentClassifier::classify()` — для не-affects возвращает null (покрывает и MailRouter, и крон `mail:classify-intent-pending`); ставит `intent_classified_at`, чтобы крон не перебирал.
- `MailRouter` reply-путь — гасит intent-classify, `attention->onClientReplied`, `ParseRequestItemsJob`. Письмо остаётся в треде (видно + доставляется), эффектов на заявку нет.

Ремонт данных M-2026-6071: status+peak_status выставлены в `quoted` напрямую (peak был раздут ручными тумблерами менеджера quoted↔awaiting_invoice + AI-переходом). Возможен исторический аудит других заявок с ai_auto_apply от внутренних отправителей — не делали.

## Reply-all ТРЕТЬЕЙ стороны (конкурент) закрывал заявку (2026-08-11, M-2026-11446)
Клиент отправил запрос НАМ И конкуренту (<адрес> → info@myzip.ru + <адрес>). Конкурент ответил всем «Нет такого у нас» → `affectsRequestStatus` возвращал true на ЛЮБОГО внешнего отправителя (`detect()===null → return true`) → InboundIntentClassifier прочитал как ОТКАЗ КЛИЕНТА → ai_auto_apply закрыл closed_lost. Фикс `InternalSenderDetector::affectsRequestStatus`: внешний отправитель, который НЕ заказчик (isSameParty по email/домену=false) И у которого заказчик среди ПОЛУЧАТЕЛЕЙ (to/cc) → return false (он адресует заказчику, а не является им = третья сторона). Обычный ответ клиента (клиент=SENDER, не в получателях) и коллеги клиента (тот же домен) не затронуты. Проверено: #71130 конкурент→false, #71090 клиент→true. Добавлен хелпер isSameParty (email или домен).
