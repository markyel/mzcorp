Отдельное направление поверх Фазы 3 (поставщики). Заказчик: ввести специалистов по снабжению; давать им топ позиций, сдерживающих выдачу КП; из раздела формировать запросы поставщикам, инициировать обновление цен и контролировать ответы. **Решения:** роль `procurement` НОВАЯ (но раздел доступен и менеджеру — частый инициатор — и РОП/директору/админу); «не дошло до КП» = статусы **new/assigned/in_progress/awaiting_client_clarification**; блокер = **только сматченные (M-артикул) с is_price_actual=false** (несматченные не трогаем); RFQ из раздела — **позиция-центрично (по M-артикулу/catalog_item)**, при актуализации цены в каталоге все заблокированные заявки получают сигнал «💰» (PriceRefreshReconciler group-2 уже умеет, см. [[suppliers-module]]).

- `Role::Procurement` ('procurement', label «Снабжение») — не request-handler; засеяна `RolesAndPermissionsSeeder` (итерирует cases). На проде роль создана + `permission:cache-reset`.
- Роуты: `/dashboard/procurement` (`procurement.index`) в группе `role:...,procurement`; procurement добавлен и в группы requests/catalog + suppliers/clients/invoices (чтобы навигировать).
- Rail «⛏ Снабжение» (`$canSeeProcurement` = procurement/manager/head_of_sales/director/admin; секретарю нет) + active в layouts/app.blade.
- `App\Livewire\Procurement\Index` (`Procurement\Index::PRE_QUOTE`): агрегат блокеров по catalog_item (DB join request_items×catalog_items×requests, is_active+catalog_item_id+is_price_actual=false+status∈PRE_QUOTE+merged_into_id null), `count(distinct requests.id)`; manual LengthAwarePaginator; сводка (#позиций/#заявок), поиск (sku/name/brand), коды заблокированных заявок (ссылки), флаг «⏳ запрошено» (есть pending supplier_inquiry_item по catalog_item). Read-only. Проверено на проде: 360 M-позиций / 203 до-КП заявок.

## Phase 4C — «замкнуть петлю»: ответы поставщиков на дашборде (commit ea28937, 2026-06-22) ✅
Деплой на прод сделан (git pull → view:clear → npm run build → queue:restart → fpm reload). Без миграций, read-side + точечный фикс парсера.
- **Фикс детекта «в работе»:** старый `in_flight` в `Procurement\Index::positions()` джойнил `supplier_inquiry_items.request_item_id → request_items.catalog_item_id` и **никогда не загорался** для procurement-RFQ (у них `request_item_id=null`). Удалён.
- **Новый `Procurement\Index::responseByCatalogId()` (#[Computed])** + столбец «Ответ поставщика» (бывш. «Статус», width 180). Агрегирует офферы по catalog_item для позиций страницы, учитывая ОБА вида RFQ через `COALESCE(supplier_inquiry_items.catalog_item_id, request_items.catalog_item_id)` (procurement + request-центричные с того же товара). Состояние с приоритетом **quoted > awaiting > refused**: 💰 best(min)-price+поставщик (+N ждём) / ⏳ ждём ответ (N) / ✖ отказ. Toggle `▸` (x-data `sup`, рядом с IQOT `open`) раскрывает строку со ВСЕМИ офферами (поставщик · цена/«до …» / причина отказа). Каталог НЕ пишем (правило #7) — только показ, снабженец выгружает цену в 1С; памятка про сигнал «💰» после импорта.
- **Фикс `SupplierOfferParser::parse()`:** eager-load `catalogItem:id,name,brand_article` + fallback имя/OEM (`brand_article`) когда `request_item_id=null` — раньше LLM сопоставлял ответ на procurement-RFQ без артикула «вслепую».
- **Прод-верификация:** COALESCE-SQL валиден на Postgres (выполнился); сейчас procurement-инквайри на проде = **0** (RFQ из «Снабжения» ещё не отправляли) → столбец показывает «—» у всех, оживёт после первого сенда/ответа. HTTP /dashboard/procurement = 302→200 (не 500), воркеры свежие.

## Личный ящик снабженца — синк, но переписка ТОЛЬКО с поставщиками (2026-08-10)
Раньше личный ящик синкался лишь для `Role::requestHandlerRoles()` = [manager, head_of_sales], Снабжение блокировалось (форма менеджера показывала «Личный ящик не подключается для этой роли»). Расцепил: `Role::mailboxSyncRoles()` = manager+head_of_sales+**procurement** (чьи личные ящики синкаются) — на него переведены `Mailbox::scopeSyncable` (её юзает `MailSyncCommand`→`->syncable()`), `MailboxOauth` guard, блейды edit/index. `requestHandlerRoles` (пул/round-robin/автоназначение) НЕ трогал — Снабжение туда не входит. **Гейт входящей:** `Mailbox::isProcurementMailbox()` (personal + владелец procurement И не request-handler); `MailRouter::route` (после loop-guard) + defense-in-depth `IncomingMailProcessor::processIfRequest` (крон mail:create-requests минует роутер) → `ingestSupplierMessage` + return, клиентская заявка НЕ создаётся. Исходящие RFQ снабженца ловит существующий `createFromOutbound`. UI: для procurement форма показывает подключение ящика + плашку «только переписка с поставщиками». Учётные данные (юзеры/пароли ящиков) заводит заказчик через /dashboard/managers — я не ввожу. На 2026-08-10 procurement-юзеров 2, ящиков ещё не подключено.
