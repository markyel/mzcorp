Авто-привязка RequestItem → CatalogItem (`request_items.catalog_item_id`) в `App\Services\Catalog\CatalogResolutionService`:
- **A (internal_sku)**: точный наш M-SKU (`M\d{4,}`) из parsed_article → `catalog_items.sku`. Доверяем безусловно.
- **B (brand_article)**: токены parsed_article (split по `,` `/`) → `sku` / `brand_article_normalized` / `articles[]` (EXISTS) + digit-signature (≥8 цифр). НЕ через LLM.
- **C (name_vector)**: pgvector hybrid (`CatalogEmbeddingService::topNByRequestItem`) + LLM rerank/validate. Это и есть «Похожие из каталога».

## Грабля коротких токенов (M-2026-3418, коммит 7dd2e03)
`articles[]` каталога содержит МУСОР от кривого импорта из MDB: у кнопки M18255 в articles лежит `"2"` (из названия «Кнопка приказа "2"»). Из-за этого `parsed_article="АИР80S6/2"` → токен «2» → B сматчил ДВИГАТЕЛЬ с КНОПКОЙ. Фикс: в B токен с нормализованной длиной < `MIN_ARTICLE_TOKEN_LEN`(=4) пропускаем (→ C-step). Побочка: легитимные 3-символьные модели (Montanari «M83», «M73», ремень «M42») B больше не ловит — но их корректно подбирает C-step по name+категории. Симптом мис-матча: `quality_assessment_payload.catalog_match.matched_token_normalized` короткий (1-3 симв).

## Категория в LLM-матчере (коммит 0e25254)
Сверять KB-категорию по **id НЕЛЬЗЯ** — у позиций заявки и каталога РАЗНЫЕ таксономии. Поэтому в LLM (rerank+validate, `CatalogEmbeddingService::rerankCandidatesWithLlm`/`validateMatchWithLlm`) передаём **названия категорий текстом**: нужная категория заявки = `RequestItem.kbCategory->name` (fallback `quality_assessment_payload.detailed_category.name`), категория кандидата = `catalog_items.part_type` (человекочитаемо, напр. «Кнопка приказной/вызывной панели»). В промптах (`RerankCatalogMatchPrompt`/`ValidateCatalogMatchPrompt`) правило: явно другой класс (двигатель vs кнопка/реле/плата) — отклонять, даже при совпавшем артикуле. **Сильный сигнал, не жёсткий фильтр** (ошибочная категория заявки → опора на название). Только C-step; A/B не трогает.

## Часть vs целое / активатор ≠ компонент (commit 838fac8, 2026-07-08)
Кейс M-2026-3710: «Контакт дверей кабины МЛЗ» → M22062 «Качалка (флажок) включения контакта дверей кабины» (C-step, trgm 0.74, llm approved_rerank). 2 дыры: (1) `requestCategoryText` не смотрел строковую `request_items.category` от парсера («Безопасность») — категория запроса уходила в LLM пустой при честной категории кандидата «Рычаг» → добавлен fallback KB→detailed_category→item.category; (2) промпты (Rerank+Validate) покрывали только «деталь ⊂ система», добавлено обратное правило: качалка/рычаг/кронштейн/крышка/ось/держатель ДЛЯ компонента X ≠ сам X, главное существительное должно совпадать (текстовое сходство обманчиво). После фикса оба этапа отклоняют качалку; регрессия на 6 свежих name-матчах — все OK. При сбросе привязки observer (RequestItemObserver→detectAndStoreItemPath) пересчитает match_path в `Manual` — это метка сложности «ручная обработка», не «привязано вручную», норм.

## Сильное имя перевешивает бренд (commit 3bf7066, 2026-07-30)
Кейс M-2026-10322 (заказ с Liftway: MyLift — поставщик, письмо БЕЗ sku — только имя+бренд «КМЗ»): позиция «Ползунок верхней направляющей ДК больничного лифта КМЗ» (артикул пустой) точно совпала по имени с каталогом M24282, но `validateMatchWithLlm` отклонил — у каталога бренд «Лифтовой Торговый Дом», у заявки «КМЗ». **Бренд в каталоге указан НЕВЕРНО** (OEM-производитель КМЗ vs торговый дом; каталог read-only, синк MDB — не правим). Прошлое правило «артикул пустой → бренд может отличаться у OEM» было слишком слабым — LLM всё равно сомневался. Фикс в `ValidateCatalogMatchPrompt`: явное правило — при (near-)exact совпадении названия + того же функционального класса расхождение ТОЛЬКО по бренду НЕ повод отвечать false (бренд в каталоге бывает мислейблен). Проверки класс/модель/параметры/часть-vs-целое остаются (см. [[item-parsing-pipeline]] не при чём — это C-step валидатор). Проверено: validateMatchWithLlm → same=true. Заметь: Liftway-заказы приходят БЕЗ sku (только имя+бренд+кол-во) → всегда C-step name-match, брендовые расхождения каталога били бы по ним систематически. Письма заказчика (LazyLift) НЕ правим — заказчик волен писать как угодно; чиним у себя.

## Exact-name fast-path + primary-бренд топит вектор (commit 133f250, 2026-08-13)
Кейс M-2026-11722: позиция «Блок VTA-CAN CPU BETACONTROL» НЕ сматчилась авто, хотя в каталоге ровно одна запись с идентичным именем (M15849, id 16820). Диагноз (прогон `CatalogEmbeddingService::topNByRequestItem`+`matchByRequestItem` на проде): ретривер поставил ТОЧНОЕ совпадение лишь 2-м (sim 0.834), а 1-м — похожую-но-ДРУГУЮ M19896 «…VTA-CAN **MOT**…» (sim 0.876), затем LLM-rerank не выбрал никого → NULL. **Корень: эмбеддинг кодирует только primary `brand`** (`buildCatalogText`/`buildQueryText` строка «Бренд: …» берёт `catalog.brand` / `parsed_brand`, НЕ `brands[]`). У точной записи primary=LiftEquip (≠ бренд клиента BETACONTROL, хотя BETACONTROL ЕСТЬ в `brands[]`) → строка бренда разошлась → вектор просел; у MOT primary=BETACONTROL → совпал → балл выше. Для коротких имён строка бренда доминирует над сутью. `isBrandSafe` при этом TRUE (смотрит все алиасы) — гейт не виноват.
**Фикс:** `CatalogResolutionService::matchByExactName` (вызывается ПЕРВЫМ в `matchByName`, до эмбеддинг+LLM): нормализованное `parsed_name` (`lower(regexp_replace(btrim(name),'\s+',' ','g'))) == ровно одна активная `catalog_items` → привязка напрямую (method `C_exact_name`, promoteStatus=false). Гарды: ровно 1 запись (0/≥2 → обычный C-step), имя ≥5 симв. Бэкфилл истории: 83 несматченные позиции получили привязку, remaining eligible=0. **Глубокий фикс (commit bbe1d03, 2026-08-13):** `buildCatalogText` теперь кодирует в вектор ВСЕ бренды (`buildBrandLine`: union primary+`brands[]`, дедуп без регистра, primary первым для 169 позиций где primary∉brands[], кап `MAX_EMBED_BRANDS=8` — у части позиций brands[] это зонтичный список до 43 брендов, длинная строка топит суть). Меняет source_hash только у строк с ≥2 брендами → `catalog:embed` (incremental=syncAll(false)) переэмбеддил 16485/30794 (~$0.05, 0 ошибок). Проверка M15849: ретрив поднял точное совпадение #2→#1 (sim 0.834→0.859, обошло MOT-двойника). **Замер до/после харнесом `catalog:match-eval --limit=80 --control=200`** (детерминизм C-tier: temperature=0+seed): контроль-регрессии почти неподвижны (сломано 12→13 из 200 = шум), эталон correct 24→24 (эталонный набор из другого распределения ошибок — артикульные легит-замены + неоднозначные имена — не ловит класс «primary=поставщик», поэтому headline-числа не двигаются, хотя ретрив реально исправлен). Мотив заказчика: primary-бренд в 1С ЧАСТО = поставщик, не производитель. Откат при регрессии был бы: revert + `catalog:embed --all`. Смежное: query-side (`buildQueryText`) НЕ трогали — клиент даёт один бренд, он теперь попадёт в мульти-список каталога.
Прогон харнеса на проде ДОЛГИЙ (~25 мин на 280 LLM-позиций) — гонять в фоне (`nohup ... > /tmp/eval.txt`), не в foreground. PsySH в пайпе глотает echo (только последнее выражение) — для prod-диагностики использовать прямой bootstrap-скрипт (`require vendor/autoload; $app=require bootstrap/app.php; $app->make(Kernel)->bootstrap();`) через `php script.php`, НЕ `artisan tinker < file`.

## Бренд в НАЗВАНИИ каталога (не только в поле brand) (fix fbc285c, 2026-08-18, M-2026-12576)
Кейс: «Контроллер эскалатора MCTC-PES-E1 Monarch» (parsed_brand=Monarch, parsed_article ПУСТОЙ → только C-step) не матчился на верный **M17326 «Блок управления Monarch MCTC-PES-E1»** (id 30452). Причина: `isBrandSafe` отсекал кандидата (`brandSafe=N`) — бренд «Monarch» есть в НАЗВАНИИ каталога, но НЕ в `brand`/`brands[]` (brand=«JF (JIEFENG E&E)», brands=[Мой ЗиП,GUANGRI,JF,KOYO]). Частый паттерн: OEM в имени, а brand-поле = дистрибьютор/изготовитель платы. Фикс в `CatalogEmbeddingService::isBrandSafe`: токен бренда клиента (≥3 симв), встречающийся в `catalog.name` или `brand_article` (substring, lower), считается валидным брендом → кандидат проходит хард-фильтр, LLM-rerank остаётся финальным судьёй (diagnose подтвердил: rerank_picked M17326 «совпадает с названием клиента»). Позиция 26234 сматчена. ГРАБЛЯ: `matchByRequestItem` иногда возвращал NULL при живом кандидате — разовые сбои LLM-rerank через OpenAI-прокси (мигает); при ответе LLM выбор верный. diagnose (`catalog:diagnose-c-rejected --item=N`) и `matchByRequestItem` дают разный пул: последний зовёт `topNByQueryText(...,$item->parsed_name)` с 4-м параметром nameOnly.

## Точечный ре-резолв после импорта (perf, commit 9c9092c, 2026-08-05)
Симптом: CPU БД ~2 ядра на 4-5 часов, ~2 раза/сутки. Причина: автосинк каталога (`catalog:sync-from-url` в 03/07/11/15/19/23 MSK, импортит только если источник менялся ~2×/сут) на ЛЮБОЙ изменяющий импорт запускал `ResolvePendingFromCatalogJob` без аргументов → ре-резолв ВСЕГО бэклога несматченных (`request_items` is_active + catalog_item_id null + pending/parsed_*) = ~6682 поз. → 1 воркер `catalog-resolve` (supervisor `--queue=catalog-resolve --tries=1`) × ~2 мин/chunk(50) → часы. Проверка: импорт #473 (2 новых SKU, 143 апдейта цен/стока) → реально к резолву 0 позиций. 100% впустую (цена/сток матчинг не меняют). Запрос сам по индексу (`<%` GIN), но объём × 1 воркер убивал.
**Fix:** `CatalogImportService::import` собирает SKU изменившихся по МАТЧИНГ-полям (created / name / name_en / brand_article; ценовые/стоковые НЕ учитываются) → `ResolvePendingFromCatalogJob::dispatch($resolveSkus)` ТОЛЬКО если такие есть. Job теперь `__construct(?array $changedSkus=null)`: точечный режим — извлекает артикул-токены (sku/brand_article/articles) изменённых SKU и фильтрует pending по `UPPER(REGEXP_REPLACE(parsed_article,'[\s._/-]','','g')) IN (токены)` (нормализация PHP=SQL!); null=полный (ручной/первичный). Безусловный full-dispatch убран из `CatalogImportCommand` и `CatalogImportController`. Диагностика нагрузки: `pg_stat_activity` (искать `word_similarity`), `jobs` where queue=catalog-resolve, `ps -eo etimes,cmd|grep queue:work`. Немедленно снять нагрузку: удалить не-reserved jobs из очереди catalog-resolve. Связано: [[prod-deploy]], [[session-2026-07]] (матчинг-бэклог 3880/1 воркер — та же боль).
