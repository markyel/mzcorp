## 1. Идея

Письма не прогоняем через конвейер, а строим заявки напрямую по номерам. Конвейер (классификатор, разбор позиций, назначение, раскладка в Яндексе, уведомления) просто не вызывается, поэтому ему неоткуда слать письма и двигать папки, а OpenAI не нужен.

Старые номера `M-2026-…` сохраняются: они уже есть у клиентов в переписке, и их ответы будут находить заявку. Новые заявки пойдут с 30001 (`request_code_sequences`, уже выставлено), пересечений нет: последний известный номер около 21800.

| Источник | Что даёт | Где в коде |
|---|---|---|
| Автоответ клиенту: тема «Ваш запрос M-2026-… принят в работу» | Номер, клиент, дата. In-Reply-To ведёт к исходному письму. Было около 105 в день (MEMORY:1141), с какой даты — неизвестно | `ClientNotificationTemplatesSeeder:51` |
| Подвал каждого письма, отправленного из CRM: «№ заявки: M-2026-…» | Номер в теле, даже если тему изменили | `OutgoingMailMimeBuilder:150` |
| Тема `[M-2026-…]` новых писем из заявки | Номер в теме, сохраняется в «Re:» | `EmailDraftService:158` |
| Ответы менеджера прямо из Яндекса | Номера может не быть, привязка по References к письму с номером | — |
| Счёт и КП: имя файла, тема, текстовый слой PDF без Vision | Тип и номер документа. Шаблоны и разбор текста уже есть | `OutboundDocumentDetector:153-168`, `PaymentDocumentDetector:221`, `Invoices/Unlinked:137` |

Номера заявок сквозные, поэтому полноту можно измерить точно: сколько номеров из 1…~21800 нашлось. Часть пропусков законна (например, закрытые без ответа заявки), но общая картина будет видна сразу.

## 3. Как будет устроено

**`retro:scan` — читает почту, ничего не решает.** С настоящими часами, через PEEK, по одному соединению на ящик.
- Читает «Отправленные» всех ящиков, INBOX и `MZ|*` с мая: заголовки всех писем, тело только исходящих. Вложения не качает, только их имена.
- Заполняет отдельный индекс: Message-ID, In-Reply-To, References, дата, ящик, папка, от кого и кому, найденные номера заявок, имена вложений.
- Письма одного Message-ID в разных ящиках схлопывает.
- Без изменений в рабочих таблицах. Можно прервать и продолжить.
- Итог — **отчёт о полноте** (§6). Нужен только вход в ящики Яндекса, ключ OpenAI не нужен.

**`retro:build` — строит из индекса.** Прямая запись в базу, без наблюдателей моделей и задач в очередь.
- Заявка на каждый номер: `internal_code`, настоящие `created_at` и `last_activity_at`, тема, клиент, связанные письма.
- **Клиент:** получатель автоответа; иначе отправитель исходного письма по In-Reply-To; иначе получатель письма из CRM, не внутренний и не поставщик.
- **Ответственный:** папка `MZ|`, в которой лежит письмо (имена из IMAP LIST); иначе автор наших ответов в цепочке; иначе без ответственного в отдельный список.
- **Письма:** цепочка по Message-ID и References привязывается к заявке, чтобы переписка открывалась в карточке.
- **КП и счета:** исходящее с подходящим именем файла скачивает только этот файл, тип определяется правилами, номер, дата и сумма берутся из текстового слоя PDF регулярными выражениями. Создаётся `OutboundQuote` и `Invoice`. Сканы и непонятное идут в список на ручной разбор, без угадывания.
- **Статус** считается один раз по итогу цепочки: есть счёт → `invoiced`, есть КП → `quoted`, есть только наш ответ → `in_progress`. Пишется в журнал с настоящей датой и пометкой «восстановлено».
- Повторяемо: база пересоздаётся миграциями, сборка повторяется из индекса, письма заново не читаем. Это позволит быстро улучшать правила.

**Страховки.** Код не вызывает ни одного пути отправки, что проверяет отдельный тест (`Mail::fake`, `Queue::fake`, ноль задач и писем). Cron и воркеры выключены до этапа 6. Ufw запрещает исходящие 25 и 587; порт 465 открыт по решению заказчика 04.11 для отправки из CRM, поэтому сетевой защиты от писем через Яндекс больше нет. Письмо может уйти только по действию в интерфейсе, пока cron и воркеры выключены.

## 5. Чего не будет без GPT

Это прямое следствие решения, важно принять его осознанно:
- **Позиций заявок.** Это главная потеря. Без них не работают таблица позиций в карточке, привязка к каталогу, поиск по артикулу в заявках, отчёты по позициям, поиск близнецов, пул QuoteParts и IQOT по старым заявкам. Варианты на потом, без пересборки: разбирать позиции GPT только для открытых заявок или по кнопке (`requests:parse-items`), либо вытащить строки из текстового слоя наших КП и счетов правилами, если шаблон стабильный. Проверим на этапе 3.
- **Заявок, по которым нет письма с номером,** ни в ответе, ни в цепочке. Сюда могут попасть заявки 25–27 мая (замер: 946 писем наружу без подвала и номера, письма из CRM с подвалом идут с 28 мая, первый номер того дня около 2305). Номера этих дней ищем по более поздним письмам той же цепочки.
- **Отказов клиента и уточнений** как статусов: их определял классификатор.
- **Категорий писем и решений маршрутизатора** (`mail_decisions`).
- **Реестра поставщиков из писем:** `suppliers:mine-from-outbound` использует GPT. Запросы поставщикам несут номер заявки, поэтому их отсеиваем правилом «получатель не клиент», а справочник ведём вручную.
- **Сумм и номеров** из сканов и нестандартных файлов.

Как и при любом варианте: `Quotation` (версии, черновики), ручные закрытия и причины, комментарии, правки менеджеров, история переназначений (`MZ|` хранит только первого ответственного), ручные флаги поставщиков и организаций. `closed_won` только из файла оплат. Отчёт об отправленных КП считается по `quotations` (`ManagerAnalyticsService:414`) и будет пустым, пока не переведём его на `OutboundQuote`.

## 9. Риски

- **Номера есть не везде.** Автоответ могли включить не с самого начала, а ответы из Яндекса могут обрывать цепочку. Этап 1 это покажет до основной разработки.
- **Цепочка ведёт к чужой заявке:** пересланные письма, письма с несколькими номерами, запросы поставщикам с номером заявки. Отдельный список конфликтов и проверка на этапе 3.
- **Шаблоны документов менялись** или КП приходит не из 1С: часть уйдёт в ручной разбор.
- **Лимиты Яндекса:** режет параллельные соединения (MEMORY:482), бывают пустые ответы (MEMORY:483). Скан идёт в один поток, письма с ошибкой повторяются и попадают в отчёт. Прежний срез бэклога терял письма (MEMORY:982), поэтому полноту сверяем с числом писем в папке.
- **Письмо без Message-ID** получает случайный ключ и дублируется (`MessagePersister:44`): для индекса считаем ключ по содержимому.
